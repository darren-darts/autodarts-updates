# Autodarts

Interactive darts scorer: 3-camera automatic dart detection, a library of
games on a shared engine, multi-player with phone join, and ESP32 LED
effects. Runs on Windows and Raspberry Pi 5. See [PLAN.md](PLAN.md) for the
full architecture.

## Layout

- `backend/` — Python FastAPI: camera capture, calibration, detection, games, LEDs, API
- `frontend/` — Vue 3 + Vite single-page app (main GUI + phone GUI)
- `led-controller/` — PlatformIO/Arduino firmware for the ESP32 driving the LED surround
- `config/` — runtime settings and calibration profiles (created on first save)
- `installer/` — launcher, Inno Setup script, Pi install script
- `tools/` — release publishing, runtime/installer builds, asset generation

## Giving it to other people

See **[DISTRIBUTION.md](DISTRIBUTION.md)**. In short: they install once from a
Setup file, and after that the app updates itself from your S3 bucket —
Updates page, Download, Install and restart. A typical update is a few
kilobytes, because files are stored by content hash and only genuinely
changed ones are downloaded (a verified real update measured 3,211 bytes).

Publishing a new version, once you are happy with it:

```bash
python tools/release.py 1.1.0 -m "What changed"
```

## Backend — first run

```bash
cd backend
py -3.11 -m venv .venv          # Windows (Pi: python3 -m venv .venv)
.venv\Scripts\pip install -r requirements.txt
```

For development with auto-reload, use `dev_server.py` rather than the bare
`uvicorn --reload` CLI — plain `--reload` watches the current working
directory recursively, which includes `backend/.venv` (thousands of
installed-package files) or, if launched from the project root, also
`frontend/node_modules`; either makes the reloader painfully slow to react
and can make it look hung. `dev_server.py` sets `reload_dirs`/excludes in
code so it always watches only `backend/`'s own source, however it's
invoked:

```bash
.venv\Scripts\python dev_server.py                    # from backend/
backend\.venv\Scripts\python backend\dev_server.py     # from the project root
```

Without reload (production-style), either the plain CLI form works fine:

```bash
.venv\Scripts\uvicorn app:app --host 0.0.0.0 --port 8000
```

On the Pi you may need `sudo apt install libgl1` for OpenCV.

## Frontend — development

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, /api proxied to :8000
```

## Production (Pi or PC)

```bash
cd frontend && npm run build
```

FastAPI serves `frontend/dist/` automatically when it exists, so the whole
app is then just the uvicorn process on port 8000.

**Note:** `--host 0.0.0.0` (not the default `127.0.0.1`) is required for a
phone to reach the server over the LAN — the home screen's QR code (below)
won't work without it, even though the QR itself will still render with
the right IP.

## Phone join (QR code)

The home screen (`/`) shows a QR code built from `GET /api/network/info`
(the server's LAN IP) plus the current port, pointing a phone at `/join`.
Scan it with a phone on the same WiFi network — `/join` opens the same
player roster described below, in a phone-sized layout.

## Players

A shared roster (`GET/POST/PATCH/DELETE /api/players`) is the single
source of truth for who's playing, editable from **either** the main
screen (`/players`) or any joined phone (`/join`) — both render the same
`PlayerRoster` component. Changes broadcast live over a WebSocket
(`/ws`, `backend/events.py`), so renaming a player or taking a selfie on
a phone updates the main screen immediately, no polling or refresh.

- Defaults to 2 players ("Player 1", "Player 2"); add/remove between 1
  and 8. Solo play is fine — the minimum is 1, not 2.
- Names are editable inline; avatars are picked from a gallery or replaced
  with a selfie taken via the phone's native camera app → captured to a
  square JPEG → `POST /api/players/{id}/selfie`.
- Roster and selfies persist to `config/players.json` / `config/selfies/`
  so the setup survives a restart.
- The default avatar gallery (`frontend/public/avatars/`) is generated by
  `tools/generate_avatars.py` — programmatic placeholder mascots, since no
  AI image-generation tool is wired up yet. Swap in real generated art by
  dropping same-named files into that folder, or point the script at an
  image API later.

### Selfies work over plain HTTP — no HTTPS needed

`SelfieCapture.vue` deliberately avoids the `getUserMedia` live-camera API,
which needs a "secure context" (HTTPS, or `localhost`) with no exception —
a phone on plain `http://<lan-ip>:8000` doesn't qualify, which used to make
the selfie button fail. Instead it uses a plain
`<input type="file" accept="image/*" capture="user">`, which hands off to
the phone's native camera app via the OS's own file picker — a different
code path that isn't gated behind a secure context, so it works over plain
HTTP on both iOS and Android. Trade-off: no live in-page preview before the
shot (you get the OS camera app's own viewfinder instead), which is a fair
swap for not needing HTTPS at all.

We initially tried enabling HTTPS with a self-signed certificate
(`tools/generate_dev_cert.py`, still in the repo, unused by default) and
backed it out — every device showed a "connection not private" warning on
first visit, bad UX for a party app. The file-input approach above made
that unnecessary for selfies specifically; the cert script remains
available if some *other* feature ever needs a secure context.

## LED surround (ESP32)

The ESP32 firmware in `led-controller/` accepts the same JSON state schema
(`on`/`bri`/`fx`/`sx`/`col`/`col2`) over two transports at once:

- **USB serial** — one JSON object per line at 115200 baud. Works the
  instant the board boots, no network needed.
- **WiFi HTTP** — `GET/POST /api/state` etc., reachable at
  `http://led-controller.local`. Connects in the background; if it can't
  join the configured network it keeps serving serial-only and retries
  periodically (see `WIFI_ENABLED`/`WIFI_SSID` in `led-controller/include/config.h`).

Build/flash with [PlatformIO](https://platformio.org/):

```bash
cd led-controller
pio run -e esp32dev -t upload      # over USB
pio run -e esp32ota -t upload      # over WiFi, once already running
```

The backend's LED hook lives at `backend/leds/controller.py` as the
`led_controller` singleton — everything else in the app (calibration,
games) is meant to call `led_controller.cue("name")` or
`led_controller.send({...})` rather than talk to the ESP32 directly.
Sends are fire-and-forget on a background thread, so a disconnected or
unplugged LED controller never blocks calibration or a game. Configure the
transport (`auto` / `serial` / `http` / `off`) on the **LEDs** page in the
web UI, which also lists detected serial ports and lets you preview
effects and cues live.
